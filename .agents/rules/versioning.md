# バージョン管理・能動的バージョンアップ提案ルール (Versioning Protocol)

## 1. 目的と理念
本プロジェクトは [セマンティック バージョニング (Semantic Versioning 2.0.0)](https://semver.org/lang/ja/) に厳格に準拠する。
AI アシスタントは「機能を追加・修正して終わり」にするのではなく、**常に現在のバージョン番号と変更の規模（メジャー / マイナー / パッチ）を意識し、適切なタイミングで能動的にバージョンアップを提案**しなければならない。

---

## 2. バージョン更新の判断基準 (SemVer 基準)
* **MAJOR (X.0.0)**:
  * 後方互換性のない破壊的変更、アーキテクチャの全面刷新、非互換な API 仕様変更
* **MINOR (1.X.0)**:
  * 後方互換性のある**新機能の追加**（新UIコンポーネント、新エンドポイント、新機能モードの導入など）
  * 複数の機能改善がまとまったマイルストーン達成時
* **PATCH (1.0.X)**:
  * 後方互換性のある**バグ修正**、スタイルの微調整、内部リファクタリング、ドキュメント修正

---

## 3. アシスタントの必須行動指針 (Proactive Proposal Trigger)
1. **実装完了時のバージョン確認・提案義務**:
   * 機能追加や改修の実装を完了した際、回答の末尾で必ず**「今回の変更に応じたバージョンアップの提案」**を行うこと。
   * 形式例:
     > 💡 **バージョン更新のご提案**:  
     > 今回の改修は「新機能の追加（○○機能、△△機能の実装）」に該当するため、現在の `v1.1.5` から **`v1.2.0`（マイナーバージョンアップ）** への引き上げを提案いたします。  
     > 同意いただける場合、`package.json`, `CHANGELOG.md` 等の一括更新とテスト検証を実施します。
2. **バージョンの「停滞」を検知した際のリマインド**:
   * パッチバージョン（例: 1.1.X）のまま機能追加が積み重なっている場合、速やかにマイナーバージョン（例: 1.2.0）への引き上げをユーザーに促すこと。
3. **バージョン整合性の厳格担保**:
   * バージョンを更新する際は、以下の全箇所を漏れなく同期し、`npm test`（`version consistency` テスト）で 100% の一致を検証すること:
     1. `package.json` (`version`)
     2. `package-lock.json` (`version`, `packages[""].version`)
     3. `CHANGELOG.md` (`## [vX.Y.Z] - YYYY-MM-DD`)
     4. `public/index.html` (`#footer-version`, `#settings-version-badge`)
     5. `server/index.js` (`pkgVer`)
     6. `server/start.js` (`pkgVer`)
     7. `server/stop.js` (`pkgVer`)

---

## 4. 他プロジェクト・新規フォルダでの開発着手時 (Cross-System Rule)
* 別のフォルダや新規リポジトリでの初回開発時には、必ず以下のようにユーザーへバージョン管理を勧めること:
  > 💡 **バージョン管理のご提案**:  
  > 「本プロジェクトでも Semantic Versioning によるバージョン管理（`package.json`, `CHANGELOG.md`, バージョン整合性テスト）を行いますか？」  
  > ユーザーが承諾した場合は、直ちにバージョン構造を整備すること。

---

## 5. コミット・リリース言語プロトコル (Commit & Release Language Protocol)
開発ログとエンドユーザー向け公開情報の役割を最適化するため、以下の**ハイブリッド運用**を厳格に適用する:
1. **Git コミットメッセージ (`git commit -m`)**:
   - **Conventional Commits 形式の英語**を原則とする（例: `feat: ...`, `fix: ...`, `chore: ...`, `refactor: ...`）。
   - CI/CD パイプライン、GitHub Actions、コミット検索ツールとの機械可読性を最大化するため。
   - 必要に応じて 2 行目以降のコミット本文（Body）に日本語の詳細を記載してよい。
2. **GitHub Releases（公開リリースページ・配布物）**:
   - **日本語（または日英併記）** で記載する。
   - タイトル形式: `Research Studio vX.Y.Z - 主要機能ハイライト`
   - 本文: BOOTH 購入者やエンドユーザーが価値と更新点を即座に把握できるよう、`CHANGELOG.md` の日本語ハイライトを反映する。
3. **CHANGELOG.md**:
   - **日本語詳細（英名併記）** のスタイルを維持する。
